# Единый пользовательский контракт кеша

В FlashCache объединяем взаимодействие FlashCache и FlashMemo в один пользовательский контракт вокруг `getOrSet`. FusionCache служит ориентиром для формы API; дополнительные механики из него не входят в объём этой переработки. Основной flow должен оставаться явно читаемым в коде.

Быстрый путь возвращает значение синхронно, в том числе при асинхронной factory. Контракт результата — `T | Promise<T>`: вызывающий код принимает эту неоднородность ради отсутствия Promise на синхронном пути. При полностью синхронных store и factory сохраняем возможность синхронного завершения промаха; существующий тип `MayBePromise` подходит для этого контракта.

После реализации и сравнения производительности v2 перенесена в основной экспорт `FlashCache`. Реализация v1, `FlashMemo` и временный экспорт `/v2` удалены без обратной совместимости. Префикс формата хранения `flashCache:v2:` сохранён; старые ключи v1 не читаются.

Сохраняем обязательные L1 и L2, существующие интерфейсы store, `ttl`, `staleRatio` и `customTtl`. Допустимое stale-значение возвращается с обновлением в фоне; expired не выдаётся. Перенос L2 → L1 не продлевает срок жизни.

Один singleflight на ключ и экземпляр охватывает чтение L2, вызов factory при необходимости и запись. Factory и параметры обновления задаёт первый вызов; обращения к одному ключу должны использовать согласованный контракт данных. Публичные операции — `getOrSet`, `get`, `set`, `delete`; `get` не запускает factory и возвращает значение либо `undefined`. Протокол `state/revalidation` между прежними классами не переносится в публичный API.

`serialize` / `deserialize` переносятся в store и не входят в опции отдельного `getOrSet`.

При ошибке чтения L2 сообщаем через `onError` и продолжаем через factory, если повторная проверка не нашла fresh L1. Ошибка записи L2 не отменяет успешное получение данных и запись в L1. Об этих ошибках сообщаем через `onError`. Эта политика продолжения работы согласована явно.

Клонирование задаётся необязательной функцией `cloneValue: (value: T) => T` на экземпляре кеша. По умолчанию возвращается общая ссылка. Клонируем только при выдаче читателю, отдельно для каждого вызова, включая участников singleflight; входные значения не клонируются. `useClones` и `materialize` из API удаляются. Пользовательская функция отвечает за сохранение типа и поведения значения и изоляцию изменяемых данных. `structuredClone` можно передать явно для совместимых с ним данных.

`get` синхронно возвращает fresh или допустимый stale из L1 без фонового обновления. При отсутствии допустимого L1 читает L2 и переносит допустимую запись с исходными сроками жизни. При miss, expired или ошибке чтения L2 возвращает `undefined`; ошибку сообщает через `onError`. `cloneValue` применяется при выдаче значения.

После factory сначала публикуем значение в L1, затем ждём завершения попытки записи L2 и возвращаем результат. Пока запись L2 выполняется, новые читатели могут получить значение из L1 синхронно. `set` также ждёт завершения попытки записи обоих уровней.

`onError` — необязательный синхронный callback `(error: unknown, context: {key: string; operation: 'l2.get' | 'l2.set' | 'refresh'}) => void`. Он сообщает об обработанных ошибках чтения/записи L2 и ошибках фонового обновления без повторного уведомления об одной ошибке. Ошибки ожидаемой factory и клонирования передаются читателю; в фоне ошибки обновления сообщает hook. Исключения самого hook перехватываются и не меняют результат операции. Без hook уведомлений нет.

`delete` удаляет L1, затем L2; ошибка удаления L2 передаётся вызывающему коду. Повторы и tombstone-записи не добавляются.

В начале `set/delete` текущий singleflight по ключу отсоединяется от кеша. Ранее начатые чтения L2 и вызовы factory продолжаются, и ожидающие читатели получают их результат (либо ошибку), но отсоединённая операция не вправе начинать запись результата в L1 или L2. Новые обращения не присоединяются к ней: используют установленное значение либо начинают новую загрузку. Завершение старой операции не должно удалить singleflight новой операции. Проверка права публикации нужна и перед переносом L2 → L1, и перед записью результата factory. Уже отправленная до отсоединения запись L2 не отменяется; это ограничение локальной координации, а не гарантия порядка операций между процессами.

Сохраняем запрет кеширования `undefined`, допустимость `null`, положительный целочисленный TTL в миллисекундах и `staleRatio` от 0 до 1. Таймауты, retry и межпроцессный singleflight в объём переработки не входят.

После ответа L2 активная операция `get/getOrSet` повторно проверяет L1. Уже опубликованное fresh-значение имеет приоритет: возвращаем его, не переносим ответ L2 и не вызываем factory. Stale/expired L1 не имеет такого приоритета. Проверка `active` сохраняется: отсоединённые операции возвращают результат своей работы без публикации и без замены его новым L1.

Политика ошибок store пересмотрена: FlashCache не различает ошибки доступа и преобразований внутри L2. Любая ошибка `get` сообщается через `onError`, затем при отсутствии fresh L1 вызывается factory (для прямого `get` возвращается `undefined`). Любая ошибка `set` сообщается через `onError`, успешный результат и L1 сохраняются. Ошибка `delete` пробрасывается. Store не обязан использовать специальные типы ошибок; `StoreTransformError` удалён. `SerializedStore` остаётся необязательным адаптером без оборачивания исключений, `IORedisStore` не наследуется от него. Это сознательно заменяет прежнюю политику пробрасывания ошибок преобразований L2 ради простого контракта store.
