# Flash Cache

Основной экспорт `FlashCache` из `@bidster/flash-cache` предоставляет `getOrSet`, `get`, `set` и `delete`.

```ts
import { FlashCache, MapStore, IORedisStore } from '@bidster/flash-cache';

const cache = new FlashCache(new MapStore<number>(), new MapStore<number>(), {
  ttl: 60_000,
  staleRatio: 0.8,
  namespace: 'counts',
  onError: (error, context) => console.error(context, error),
});

const count = cache.getOrSet('users', () => loadUserCount());
// Fresh L1 возвращает число синхронно, даже если loadUserCount асинхронна.
// На промахе асинхронная загрузка или запись L2 приводит к Promise<number>.
if (count instanceof Promise) {
  count.then((value) => console.log(value)).catch(console.error);
} else {
  console.log(count); // Синхронная обработка без await.
}
```

## Синхронность — часть контракта

`MayBePromise<T> = T | Promise<T>` не оборачивает все результаты в Promise. Вызывающий код может обработать обычное значение сразу, в том же стеке вызовов. Тип результата определяется фактически пройденным путём, а не только тем, объявлена ли factory как `async`.

| Путь                                            | Результат для читателя                                                  |
| ----------------------------------------------- | ----------------------------------------------------------------------- |
| Fresh L1 в `getOrSet`                           | Значение синхронно; нет Promise, чтения L2 и вызова factory             |
| Допустимый stale L1 в `getOrSet`                | Значение синхронно; обновление может быть асинхронным                   |
| Допустимый fresh/stale из синхронного L2        | Значение синхронно; stale не ждёт обновления                            |
| Чтение асинхронного L2 без допустимого L1       | Promise; при stale ответ не ждёт завершения обновления                  |
| Промах при синхронных store и factory           | Значение синхронно                                                      |
| Промах с асинхронной factory или записью L2     | Promise, ожидающий загрузку и попытку записи L2                         |
| Присоединение к singleflight без допустимого L1 | Promise, даже если другие читатели уже получили stale                   |
| `get`                                           | Значение или `undefined` синхронно при синхронном чтении; иначе Promise |
| `set/delete`                                    | `undefined` при синхронной записи/удалении L2; иначе Promise<void>      |

Синхронный промах не означает отсутствия внутренних Promise: они используются для singleflight. Гарантия отсутствия создаваемых кешем Promise относится к fresh L1. На stale-пути возвращаемое значение синхронно, но фоновая работа может создавать Promise.

Чтобы сохранить этот контракт в своём методе, возвращайте значение или цепочку Promise в зависимости от результата и не объявляйте метод `async`:

```ts
import type { MayBePromise } from '@bidster/flash-cache';

function getUserCountLabel(): MayBePromise<string> {
  const result = cache.getOrSet('users', () => loadUserCount());
  const format = (count: number) => `Users: ${count}`;
  return result instanceof Promise ? result.then(format) : format(result);
}
```

Можно всегда использовать `await`, если синхронное продолжение не требуется. Однако `await` даже обычного значения переносит продолжение в микрозадачу. Обёртка `async` или `Promise.resolve(result)` также делает внешний интерфейс всегда асинхронным. Синхронная `cloneValue` сохраняет способ возврата исходного чтения.

При обработке без `await` учитывайте оба способа передачи ошибок:

```ts
try {
  const result = cache.getOrSet('users', () => loadUserCount());
  if (result instanceof Promise) {
    result.then((count) => console.log(count)).catch(console.error);
  } else {
    console.log(result);
  }
} catch (error) {
  console.error(error); // Синхронная ошибка вызова или обработки результата.
}
```

Один `try/catch` без ожидания Promise не перехватывает его отклонение. Политика ошибок L2 и фонового обновления при этом не меняется: обработанные кешем ошибки сообщаются через `onError` согласно разделу «Ошибки».

## Получение данных

`getOrSet(key, factory, {customTtl?, customStaleRatio?, codec?, cloneValue?})` возвращает `MayBePromise<T>` (`T | Promise<T>`). На свежем L1 не создаются Promise и не вызывается L2. Полностью синхронные store и factory позволяют завершить промах синхронно.

- Fresh L1 возвращается сразу.
- Допустимый stale возвращается читателю, а обновление проверяет L2 и при необходимости вызывает factory. Это относится и к stale, найденному в L2; одновременно ожидающие читатели могут получить его до завершения factory.
- При miss или expired читаем L2, затем при необходимости вызываем factory.
- После ответа L2 активная операция повторно читает L1. Если там уже есть fresh-значение, оно возвращается без перезаписи L1 и без вызова factory. Stale или expired L1 не блокирует использование результата L2.
- Один singleflight на ключ и экземпляр объединяет цикл L2 → factory → запись. Первый вызов определяет factory, TTL, staleRatio и codec, но не клонирование для других читателей; обращения к одному ключу должны использовать согласованный контракт данных.
- Результат factory сначала записывается в L1, затем ожидается попытка записи L2. Новые читатели уже могут читать опубликованный L1 синхронно.

TTL измеряется в миллисекундах и должен быть положительным целым. `staleAt = time + ttl * staleRatio`, `expAt = time + ttl`; `staleRatio` находится в диапазоне [0, 1]. `customTtl` и `customStaleRatio` переопределяют настройки экземпляра при загрузке источника или явном `set`. `customStaleRatio` должен быть конечным числом в диапазоне `[0, 1]`: `0` означает stale сразу после публикации, `1` — fresh до истечения TTL. Проверка выполняется перед factory или записью через `set`; на попадании в кеш опции не меняют и не перепроверяют сроки существующей записи. Переопределение не запоминается как настройка ключа: для следующего обновления его нужно передать снова. Перенос L2 → L1 не продлевает сроки. Значение expired не выдаётся; ошибка обновления не продлевает TTL.

`get(key, {codec?, cloneValue?})` возвращает `MayBePromise<T | undefined>`. Допустимые fresh/stale из L1 выдаются синхронно, без обновления. При их отсутствии читается L2. После ответа L2 также повторно проверяется fresh L1. При отсутствии fresh L1 и miss, expired или ошибке чтения L2 возвращается `undefined`; factory не запускается. Прямые `get` не объединяются в singleflight, но защищены от поздней публикации после `set/delete`.

`null` можно кешировать, `undefined` зарезервирован для промаха и запрещён при записи и в результате factory.

## Jitter момента stale

Чтобы разнести начало обновления по ключам, можно менять интервал до stale, оставляя полный TTL неизменным. Существующая функция `jitter(durationMs, percent)` уменьшает переданный интервал на случайную величину до указанной доли (с округлением случайного смещения вниз до миллисекунд).

```ts
import { jitter } from '@bidster/flash-cache';

const ttlMs = 24 * 60 * 60 * 1000;
const freshForMs = 5 * 60 * 1000;

function getUserCount() {
  return cache.getOrSet('users', () => loadUserCount(), {
    customTtl: ttlMs,
    customStaleRatio: jitter(freshForMs, 0.2) / ttlMs,
  });
}
```

В этом примере запись хранится 24 часа, а stale начинается примерно через 4–5 минут после публикации. Для `set` используются те же опции. Если задан базовый коэффициент, вместо `freshForMs` можно передать `ttlMs * baseStaleRatio`. Передавайте в `jitter` длительность в миллисекундах, а не сам коэффициент: округление внутри функции не рассчитано на дробные значения порядка `0.01`.

Новое случайное значение вычисляется при вызове обёртки, но влияет на запись только при factory-загрузке или `set`. Попадание в кеш не сдвигает `staleAt`; при singleflight используются опции первого вызова. Jitter не запускает таймер: обновление начинается при обращении к уже stale-записи.

При фиксированном коэффициенте процентный jitter TTL даёт такой же относительный разброс интервала до stale: `staleDelay = ttl * staleRatio`. Однако он одновременно меняет и срок хранения. Jitter через `customStaleRatio` позволяет независимо задавать нужное окно начала stale и сохранять TTL.

## Запись, удаление и выполняющиеся загрузки

`set(key, value, {customTtl?, customStaleRatio?, codec?})` и `delete(key)` возвращают `MayBePromise<void>`.

В начале `set/delete` текущая загрузка отсоединяется от кеша. Уже ожидающие читатели получают её результат либо ошибку, но отсоединённые чтения L2 и factory больше не могут начинать публикацию в L1/L2. Новые обращения используют значение после `set` либо начинают новую загрузку после `delete`. Отсоединённые операции не используют повторную проверку L1 для подмены своего результата новым значением: их читатели получают результат ранее начатой работы, без публикации. Завершение отсоединённой операции не очищает новую singleflight-операцию.

Это гарантия внутри экземпляра. Запись L2, уже отправленную до отсоединения, отменить невозможно. Межпроцессной координации нет.

`delete` удаляет L1, затем L2. Ошибка удаления L2 пробрасывается; запись в L2 в таком случае может сохраниться.

## Ссылки и клонирование

По умолчанию возвращается общая ссылка. Не изменяйте данные, если они должны оставаться общими и неизменными. Необязательная функция `cloneValue` передаётся в опциях `getOrSet` или `get` и применяется только к результату этого вызова, включая присоединение к singleflight:

```ts
const cache = new FlashCache<User>(l1, l2, {
  ttl: 60_000,
  staleRatio: 0.8,
});
const user = await cache.getOrSet('user:42', loadUser, { cloneValue: (value) => value.clone() });
const copy = await cache.get('user:42', { cloneValue: (value) => value.clone() });
```

Функция должна синхронно сохранять тип и поведение значения, не менять оригинал и изолировать изменяемые данные. Для совместимых данных можно явно передать `structuredClone`. Входящие значения `set` и factory не клонируются. Ошибка клонирования затрагивает только конкретного читателя и не отменяет сохранение общих данных.

При отсутствии `cloneValue` возвращается общая ссылка независимо от опций других читателей. `get` не вызывает клонирование для `undefined`. Клонирование не добавляет асинхронности к синхронному чтению. Настройка `cloneValue` на экземпляре удалена без обратной совместимости; `set` принимает только `{customTtl?, customStaleRatio?, codec?}`. `useClones` и `materialize` отсутствуют.

## Преобразования хранения: codec конкретного вызова

`FlashCache<T>` задаёт только тип значения в L1. L2 подключается напрямую и может хранить другое представление. В опциях `getOrSet/get/set` можно передать одну пару синхронных функций `codec: { serialize, deserialize }`. Тип представления L2 выводится из codec вызова; второй generic экземпляра не требуется. `SerializedStore` и его экспорт удалены без обратной совместимости.

```ts
import Redis from 'ioredis';
import { FlashCache, IORedisStore, MapStore } from '@bidster/flash-cache';

const tagsCache = new FlashCache<Set<string>>(new MapStore<Set<string>>(), new IORedisStore(new Redis()), {
  ttl: 60_000,
  staleRatio: 0.8,
});
const tags = await tagsCache.getOrSet('tags', () => new Set(['typescript']), {
  codec: {
    serialize: (value: Set<string>) => [...value],
    deserialize: (value: string[]) => new Set(value),
  },
});
```

L1 хранит исходный `Set<string>`, L2 — запись со значением `string[]`. `IORedisStore` сам преобразует запись в JSON и обратно: вызывать `JSON.stringify/parse` в codec не нужно. Без преобразования `Set` превратился бы в `{}`.

Codec применяется только при переходах L1/источник → L2 и L2 → L1. Метаданные времени не преобразуются. Промахи и expired-записи не передаются в `deserialize`. Fresh L1 не вызывает codec и остаётся синхронным. После factory сначала публикуется исходное значение в L1, затем выполняется `serialize` и запись L2. После чтения L2 выполняется `deserialize`, и восстановленное значение становится доступно L1 и читателям. `cloneValue` вызывается отдельно для каждого читателя уже после восстановления значения.

Первый вызов singleflight определяет codec всего цикла; codec присоединившихся читателей не вызываются. Все обращения к одному ключу обязаны использовать совместимые преобразования и один тип значения, в том числе `get/set`. Нет центрального реестра, запоминания codec или сравнения функций по ссылке. Удобно объявить пару рядом с загрузчиком и передавать её при каждом обращении к ключу.

Без codec значение передаётся без преобразований. Это простой необязательный параметр: типы не делают его обязательным при потенциальном несовпадении L1/L2. Вызывающий код отвечает за соответствие результата `serialize` возможностям store и за тип данных, ожидаемый `deserialize`. Ошибка конфигурации может быть незаметна на попаданиях L1 и проявиться только на чтении L2.

Функции должны быть синхронными, не менять входящие значения и не возвращать `undefined`. Ошибка `deserialize` сообщается как `l2.get`, затем при отсутствии fresh L1 вызывается factory; прямой `get` возвращает `undefined`. Ошибка `serialize` сообщается как `l2.set`, успешный результат и опубликованный L1 сохраняются. Ошибки не оборачиваются. `delete` не требует codec. Защита отсоединённых загрузок действует и при повторном входе через codec. Прямой `set` также проверяет актуальность публикации после `serialize`: вложенный `set/delete` отменяет ещё не отправленную запись L2 внешнего вызова. Типы codec запрещают возвращать Promise/thenable, включая вывод промежуточного типа из `serialize`; свойство `then` в результате зарезервировано и не должно быть задано.

## Обёртки Redis-команд

В `IORedisStore` обращения к Redis выделены в protected-методы:

- `read(key: string): Promise<string | null>` — команда `GET`.
- `write(key: string, raw: string, expAt: number): Promise<void>` — команда `SET` с сериализованным JSON и абсолютным сроком истечения в миллисекундах (`PXAT`).
- `remove(key: string): Promise<void>` — команда `DEL`.

Наследник может оборачивать эти методы, сохраняя публичные `get/set/delete` базового класса. Например, с заранее созданным экземпляром `circuitBreaker`:

```ts
class CircuitBreakerIORedisStore extends IORedisStore {
  protected override read(key: string): Promise<string | null> {
    return circuitBreaker.execute(() => super.read(key));
  }

  protected override write(key: string, raw: string, expAt: number): Promise<void> {
    return circuitBreaker.execute(() => super.write(key, raw, expAt));
  }

  protected override remove(key: string): Promise<void> {
    return circuitBreaker.execute(() => super.remove(key));
  }
}
```

`JSON.stringify` выполняется до вызова `write`, а `JSON.parse` — после успешного завершения `read`. Ошибки преобразований не попадают в обёртку Redis-команд. Обёртка может отклонить операцию до обращения к Redis; её ошибки передаются вызывающему коду без изменений. Клиент Redis остаётся приватной деталью базового класса.

## Ошибки

`onError(error, {key, operation})` — необязательный синхронный callback. `key` — пользовательский ключ без префикса, `operation` — `l2.get`, `l2.set` или `refresh`.

- Ошибка чтения L2 сообщается как `l2.get`. После повторной проверки fresh L1, если свежего значения нет, `getOrSet` продолжает через factory, а `get` возвращает `undefined`.
- Ошибка записи L2 сообщается как `l2.set`; успешный результат и значение в L1 сохраняются.
- Ошибки фонового обновления сообщаются как `refresh`. Одна обработанная ошибка L2 повторно не сообщается.
- Ошибки ожидаемой factory, L1 и клонирования передаются читателю. Если обновление уже выполняется в фоне, его ошибка передаётся в `onError`.
- Исключение из `onError` перехватывается и не меняет результат операции. Без callback уведомлений нет.

Автоматические retry, таймауты и выдача expired при ошибке не реализованы.

## Пространство ключей

По умолчанию ключи имеют префикс `flashCache:v2:`. `namespace` добавляет сегмент к этому префиксу; `namespace: false` полностью отключает его. Префикс формата хранения `flashCache:v2:` сохранён при переносе реализации в основной экспорт. Старое пространство `flashCache:v1:` не читается; миграции записей и совместимого API нет.
