# Flash Cache

Основной экспорт `FlashCache` из `@bidster/flash-cache` предоставляет `getOrSet`, `get`, `set` и `delete`.

```ts
import { FlashCache, MapStore, IORedisStore } from '@bidster/flash-cache';

const cache = new FlashCache(new MapStore<number>(), new MapStore<number>(), {
  ttl: 60_000,
  staleRatio: 0.8,
  namespace: 'counts',
  onError: (error, context) => console.error(context, error),
});

const count = cache.getOrSet('users', () => loadUserCount());
// Fresh L1 возвращает число синхронно, даже если loadUserCount асинхронна.
// При асинхронной загрузке или записи L2 возвращается Promise<number>.
const resolvedCount = await count;
```

## Получение данных

`getOrSet(key, factory, {customTtl?, cloneValue?})` возвращает `MayBePromise<T>` (`T | Promise<T>`). На свежем L1 не создаются Promise и не вызывается L2. Полностью синхронные store и factory позволяют завершить промах синхронно.

- Fresh L1 возвращается сразу.
- Допустимый stale возвращается читателю, а обновление проверяет L2 и при необходимости вызывает factory. Это относится и к stale, найденному в L2; одновременно ожидающие читатели могут получить его до завершения factory.
- При miss или expired читаем L2, затем при необходимости вызываем factory.
- После ответа L2 активная операция повторно читает L1. Если там уже есть fresh-значение, оно возвращается без перезаписи L1 и без вызова factory. Stale или expired L1 не блокирует использование результата L2.
- Один singleflight на ключ и экземпляр объединяет цикл L2 → factory → запись. Первый вызов определяет factory и TTL, но не клонирование для других читателей; обращения к одному ключу должны использовать согласованный контракт данных.
- Результат factory сначала записывается в L1, затем ожидается попытка записи L2. Новые читатели уже могут читать опубликованный L1 синхронно.

TTL измеряется в миллисекундах и должен быть положительным целым. `staleAt = time + ttl * staleRatio`, `expAt = time + ttl`; `staleRatio` находится в диапазоне [0, 1]. `customTtl` применяется при загрузке источника или явном `set`. Перенос L2 → L1 не продлевает сроки. Значение expired не выдаётся; ошибка обновления не продлевает TTL.

`get(key, {cloneValue?})` возвращает `MayBePromise<T | undefined>`. Допустимые fresh/stale из L1 выдаются синхронно, без обновления. При их отсутствии читается L2. После ответа L2 также повторно проверяется fresh L1. При отсутствии fresh L1 и miss, expired или ошибке чтения L2 возвращается `undefined`; factory не запускается. Прямые `get` не объединяются в singleflight, но защищены от поздней публикации после `set/delete`.

`null` можно кешировать, `undefined` зарезервирован для промаха и запрещён при записи и в результате factory.

## Запись, удаление и выполняющиеся загрузки

`set(key, value, {customTtl?})` и `delete(key)` возвращают `MayBePromise<void>`.

В начале `set/delete` текущая загрузка отсоединяется от кеша. Уже ожидающие читатели получают её результат либо ошибку, но отсоединённые чтения L2 и factory больше не могут начинать публикацию в L1/L2. Новые обращения используют значение после `set` либо начинают новую загрузку после `delete`. Отсоединённые операции не используют повторную проверку L1 для подмены своего результата новым значением: их читатели получают результат ранее начатой работы, без публикации. Завершение отсоединённой операции не очищает новую singleflight-операцию.

Это гарантия внутри экземпляра. Запись L2, уже отправленную до отсоединения, отменить невозможно. Межпроцессной координации нет.

`delete` удаляет L1, затем L2. Ошибка удаления L2 пробрасывается; запись в L2 в таком случае может сохраниться.

## Ссылки и клонирование

По умолчанию возвращается общая ссылка. Не изменяйте данные, если они должны оставаться общими и неизменными. Необязательная функция `cloneValue` передаётся в опциях `getOrSet` или `get` и применяется только к результату этого вызова, включая присоединение к singleflight:

```ts
const cache = new FlashCache<User>(l1, l2, {
  ttl: 60_000,
  staleRatio: 0.8,
});
const user = await cache.getOrSet('user:42', loadUser, { cloneValue: (value) => value.clone() });
const copy = await cache.get('user:42', { cloneValue: (value) => value.clone() });
```

Функция должна синхронно сохранять тип и поведение значения, не менять оригинал и изолировать изменяемые данные. Для совместимых данных можно явно передать `structuredClone`. Входящие значения `set` и factory не клонируются. Ошибка клонирования затрагивает только конкретного читателя и не отменяет сохранение общих данных.

При отсутствии `cloneValue` возвращается общая ссылка независимо от опций других читателей. `get` не вызывает клонирование для `undefined`. Клонирование не добавляет асинхронности к синхронному чтению. Настройка `cloneValue` на экземпляре удалена без обратной совместимости; `set` принимает только `{customTtl?}`. `useClones` и `materialize` отсутствуют.

## Преобразования хранения

Оба store предоставляют кешу одинаковый тип данных. Физическое представление L2 настраивается в store, а не в каждом вызове `getOrSet`:

```ts
import { SerializedStore } from '@bidster/flash-cache';

const l2 = new SerializedStore(new MapStore<string>(), {
  serialize: (user: User) => user.name,
  deserialize: (name) => new User(name),
});
```

Адаптер сохраняет временные метки и синхронность исходного store. Его также можно использовать поверх `IORedisStore`, который хранит JSON-совместимые значения. Обычные JSON-данные можно передавать непосредственно в `IORedisStore` без адаптера.

Store реализует только `get/set/delete`, без специальных типов ошибок. `SerializedStore` — необязательный адаптер: он не перехватывает ошибки преобразований и не оборачивает их. `IORedisStore` остаётся самостоятельным store.

FlashCache обрабатывает ошибку по операции L2, независимо от её причины. Ошибка десериализации вызывает `onError` и продолжение через factory при отсутствии fresh L1; при прямом `get` — `undefined`. Ошибка сериализации записи вызывает `onError`, но успешный результат и опубликованный L1 сохраняются. В hook передаётся исходная ошибка. Транзакционность между уровнями не обещается.

## Ошибки

`onError(error, {key, operation})` — необязательный синхронный callback. `key` — пользовательский ключ без префикса, `operation` — `l2.get`, `l2.set` или `refresh`.

- Ошибка чтения L2 сообщается как `l2.get`. После повторной проверки fresh L1, если свежего значения нет, `getOrSet` продолжает через factory, а `get` возвращает `undefined`.
- Ошибка записи L2 сообщается как `l2.set`; успешный результат и значение в L1 сохраняются.
- Ошибки фонового обновления сообщаются как `refresh`. Одна обработанная ошибка L2 повторно не сообщается.
- Ошибки ожидаемой factory, L1 и клонирования передаются читателю. Если обновление уже выполняется в фоне, его ошибка передаётся в `onError`.
- Исключение из `onError` перехватывается и не меняет результат операции. Без callback уведомлений нет.

Автоматические retry, таймауты и выдача expired при ошибке не реализованы.

## Пространство ключей

По умолчанию ключи имеют префикс `flashCache:v2:`. `namespace` добавляет сегмент к этому префиксу; `namespace: false` полностью отключает его. Префикс формата хранения `flashCache:v2:` сохранён при переносе реализации в основной экспорт. Старое пространство `flashCache:v1:` не читается; миграции записей и совместимого API нет.
