# @bidster/flash-cache

[English version](README.md)

Двухуровневый кэш для Node.js с синхронным чтением локальных данных, асинхронным вторичным хранилищем и мемоизацией с обновлением устаревших значений в фоне — stale-while-revalidate.

`FlashCache` управляет записями в **L1** (синхронное хранилище) и **L2** (синхронное или асинхронное хранилище). `FlashMemo` добавляет загрузку из источника, объединяет одновременные загрузки, по умолчанию клонирует локальные данные и может материализовать отдельный результат для каждого читателя. Для хранения в памяти используйте `MapStore`, для общего L2 в Redis — `IORedisStore`.

## Установка

```bash
npm install @bidster/flash-cache ioredis
# или
yarn add @bidster/flash-cache ioredis
```

Пакет предоставляет точки входа ESM и CommonJS и декларации TypeScript. `ioredis` 5 объявлен как peer dependency; `IORedisStore` использует его для доступа к Redis. Для клонирования при мемоизации по умолчанию нужен API `structuredClone` в среде выполнения.

## Быстрый старт

```typescript
import {
  FlashCache,
  FlashMemo,
  MapStore,
} from '@bidster/flash-cache';

type User = { id: string; name: string };

const cache = new FlashCache<User>(
  new MapStore<User>(),
  new MapStore<User>(),
  { ttl: 60_000, staleRatio: 0.8, namespace: 'users' },
);
const memo = new FlashMemo(cache);

const user = await memo.memoize('42', async () => {
  const response = await fetch('https://api.example.com/users/42');
  if (!response.ok) throw new Error(`User request failed: ${response.status}`);
  return await response.json() as User;
});

console.log(user.name);
```

Первый вызов загружает пользователя и сохраняет его в кэш. Пока запись свежая, следующие вызовы используют L1 и не вызывают загрузчик. Когда L1 устаревает, вызов сразу возвращает ещё допустимое значение и проверяет L2 в фоне. Загрузчик запускается только тогда, когда эта проверка не находит свежего значения.

Чтобы использовать Redis как L2, замените второй `MapStore`:

```typescript
import { Redis } from 'ioredis';
import {
  FlashCache,
  FlashMemo,
  IORedisStore,
  MapStore,
  type JsonValue,
} from '@bidster/flash-cache';

const redis = new Redis('redis://localhost:6379');
const cache = new FlashCache<JsonValue>(
  new MapStore<JsonValue>(),
  new IORedisStore(redis),
  { ttl: 60_000, staleRatio: 0.8, namespace: 'users' },
);
const memo = new FlashMemo(cache);

await cache.set('42', { id: '42', name: 'Igor' });
console.log(await memo.memoize('42', () => ({ id: '42', name: 'Igor' })));

// При завершении приложения закройте принадлежащий ему клиент.
await redis.quit();
```

## TTL и проверка актуальности

Все интервалы задаются в миллисекундах. `ttl` должен быть положительным целым числом, а `staleRatio` — конечным числом от `0` до `1` включительно. Оба параметра обязательны.

При записи сохраняются `time`, `staleAt` и `expAt`. Для выбранного TTL:

```text
staleAt = начало записи + ttl × staleRatio
expAt   = начало записи + ttl
```

При `ttl: 10_000` и `staleRatio: 0.4` запись свежая первые четыре секунды, следующие шесть секунд она устаревшая, но допустимая, а на десятой секунде истекает. `staleRatio: 1` сохраняет свежесть до истечения TTL; `staleRatio: 0` делает запись устаревшей сразу.

Чтение и перенос из L2 сохраняют исходные временные метки. Новый срок жизни начинается только при новой записи. Истечение проверяется при чтении и само по себе не удаляет запись из хранилища в памяти.

### Чтение через `FlashCache`

`cache.get(key, deserialize?)` возвращает `CacheResult<T>` напрямую, если L1 содержит допустимое значение, и `Promise<CacheResult<T>>`, если нужно дождаться L2.

| Статус | Значение |
| --- | --- |
| `fresh` | Доступно свежее значение; при попадании в L1 чтение L2 не выполняется. |
| `revalidating` | Сразу возвращается устаревшее, но не истёкшее значение L1 и выполняющаяся проверка L2 в `revalidation`. |
| `stale` | Проверка L2 завершилась без получения свежего значения; доступно устаревшее, но не истёкшее значение. |
| `expired` | Допустимого значения нет, найдена истёкшая запись. Возвращённые данные пригодны только для диагностики. |
| `miss` | Не найдено ни допустимой, ни истёкшей записи. |

```typescript
const result = await cache.get('42');

if (result.state === 'revalidating') {
  console.log('Допустимое локальное значение:', result.value);
  const checked = await result.revalidation;
  console.log('Результат проверки L2:', checked.state, checked.value);
} else if (result.state === 'fresh' || result.state === 'stale') {
  console.log('Допустимое значение:', result.value);
}
```

`await cache.get()` **не ждёт** завершения `revalidation`. Исходный результат остаётся снимком со статусом `revalidating` после завершения проверки. Чтобы получить окончательный результат, дождитесь его промиса `revalidation`.

Свежая или устаревшая запись L2 переносится в L1. Если запись L2 отсутствует, истекла или L2 недоступен, проверка повторно читает L1 и возвращает локальное значение, если оно ещё не истекло. Если L1 истёк за время ожидания, окончательный результат будет `expired` или `miss`.

Чтобы сохранить синхронное чтение на часто выполняемом пути, ожидайте только реальные промисы:

```typescript
const pending = cache.get('42');
const result = pending instanceof Promise ? await pending : pending;
```

`FlashCache` только проверяет L2 и не вызывает загрузчик из источника. Для обновления данных из базы, API или вычисления используйте `FlashMemo`.

## Мемоизация

```typescript
memo.memoize(key, loader, {
  customTtl: 30_000,
  useClones: true,
});
```

Загрузчик может вернуть значение или промис. `memoize()` также возвращает значение или промис в зависимости от пути чтения.

| Результат чтения | Поведение `FlashMemo` |
| --- | --- |
| Свежий L1 | Сразу возвращает значение, не вызывает загрузчик. |
| L1 в состоянии `revalidating` | Сразу возвращает локальное значение; ждёт L2 перед решением о запуске загрузчика. |
| Свежий L2 | Возвращает значение L2, не вызывает загрузчик. |
| Устаревшее значение после проверки L2 | Возвращает устаревшее значение и загружает замену в фоне. |
| Промах или истечение | Ждёт загрузчик и запись в кэш, затем возвращает загруженное значение. |

Одновременные загрузки одного ключа объединяются в одно обновление внутри экземпляра `FlashMemo`. Обновление включает проверку L2, загрузку из источника при необходимости и запись. Первый участвующий вызов задаёт загрузчик, функции сериализации и TTL; используйте согласованные параметры для каждого ключа.

`customTtl` заменяет TTL кэша при записи результата загрузчика. Он должен быть положительным целым числом и проверяется только тогда, когда нужна загрузка из источника. Параметр доступен через `memoize()`, а не через публичный API `cache.set()`.

`undefined` нельзя сохранять в кэш или возвращать из загрузчика: это вызывает ошибку и исключено из API TypeScript. `null` допустим и может обозначать закэшированное отсутствие данных.

### Клонирование и ссылки

`FlashCache` не клонирует значения: L1 сохраняет исходную ссылку при записи, а чтение возвращает ссылки на сохранённые значения. Синхронный L2 на основе Map тоже сохраняет ссылки, если сериализатор не создаёт отдельное значение.

`FlashMemo` по умолчанию использует `useClones: true` для каждого вызова. Для объектов и функций применяется `structuredClone`, примитивы возвращаются напрямую. Клонирование распространяется на попадания в кэш, десериализованные значения и результаты загрузчика; одновременные вызовы получают отдельные копии.

```typescript
const value = await memo.memoize('42', () => ({ name: 'Igor' }), {
  useClones: false,
});
```

При `useClones: false` вызывающий код получает общие ссылки и самостоятельно управляет мутациями. `structuredClone` сохраняет поддерживаемые встроенные типы и циклические ссылки, но не сохраняет прототипы и методы пользовательских классов. Неподдерживаемые значения, например функции, вызывают ошибку клонирования. Чтобы возвращать независимые экземпляры классов с методами, сохраняйте их данные и создавайте экземпляры через `materialize` после клонирования. Существующие экземпляры, восстановленные десериализатором, можно возвращать с `useClones: false`; при этом ссылки будут общими.

### Материализация результата

`materialize(data)` — необязательная синхронная функция, которая превращает локальные данные кэша в возвращаемое значение. Тип результата может отличаться от типов L1 и L2 и выводится TypeScript. Без материализатора `memoize()` возвращает локальное значение с выбранным режимом клонирования.

Три преобразования отвечают за разные этапы:

| Преобразование | Когда выполняется | Назначение |
| --- | --- | --- |
| `serialize` | При записи локальных данных в L2 | Перевести данные L1 в представление для хранения в L2. |
| `deserialize` | При чтении L2 | Восстановить данные, которые будут перенесены в L1. |
| `materialize` | При возврате данных читателю memo, после клонирования | Создать результат, например экземпляр класса или представление данных. |

```text
Попадание в L1 / десериализованный L2 / результат загрузчика
                            ↓
         клонирование локальных данных (useClones: true)
                            ↓
                     materialize(data)
                            ↓
                  результат для читателя
```

Храните в L1 данные, поддерживаемые `structuredClone`, и создавайте экземпляры классов при выдаче результата:

```typescript
import { FlashCache, FlashMemo, MapStore } from '@bidster/flash-cache';

type UserData = { name: string; preferences: { theme: string } };

class User {
  constructor(readonly data: UserData) {}

  greeting(): string {
    return `Hello, ${this.data.name}`;
  }
}

const local = new MapStore<UserData>();
const cache = new FlashCache<UserData>(
  local,
  new MapStore<UserData>(),
  { ttl: 60_000, staleRatio: 0.8 },
);
const memo = new FlashMemo(cache);
const loadUser = (): UserData => ({
  name: 'Igor', preferences: { theme: 'light' },
});
const materializeUser = (data: UserData): User => new User(data);

const user = await memo.memoize('42', loadUser, { materialize: materializeUser });
user.data.preferences.theme = 'dark';
console.log(user.greeting()); // Hello, Igor; метод сохранён.

const next = await memo.memoize('42', loadUser, { materialize: materializeUser });
console.log(next.data.preferences.theme); // light; данные кэша не изменились.
```

Экземпляр класса создаётся после клонирования и повторно не клонируется. В кэше сохраняется только `UserData`. Попадание в свежий или ещё допустимый устаревший L1 по-прежнему возвращает результат синхронно. Чтение L2 и загрузка из источника сохраняют прежнее асинхронное поведение.

Материализация выполняется один раз для каждого читателя при каждом успешном возврате: для попаданий в кэш, устаревших значений и результатов загрузчика. Одновременные вызовы, ожидающие общую загрузку, отдельно клонируют данные и вызывают свои материализаторы. Фоновое обновление сохраняет данные без создания неиспользуемого результата. Читатели могут использовать разные материализаторы для одного ключа, сохраняя согласованность загрузчика, типов кешируемых данных и сериализации.

Сериализацию и материализацию можно совместить, если L2 использует другое представление:

```typescript
const serializedCache = new FlashCache<UserData, string>(
  new MapStore<UserData>(),
  new MapStore<string>(),
  { ttl: 60_000, staleRatio: 0.8 },
);
const serializedMemo = new FlashMemo(serializedCache);
const serializedUser = await serializedMemo.memoize('42', loadUser, {
  serialize: JSON.stringify,
  deserialize: (stored: string): UserData => JSON.parse(stored),
  materialize: materializeUser,
});
console.log(serializedUser.greeting());
```

Здесь L2 хранит JSON-строку, L1 хранит `UserData`, а читатель получает `User`. Материализатор не заменяет обязательный десериализатор. Он должен принимать весь локальный тип L1: более узкий тип результата загрузчика не сужает тип существующих попаданий в L1. Переиспользуемые настройки можно описать типом `MaterializedMemoizeOptions<UserData, User>`, а сам callback — `MemoizeMaterializer<UserData, User>`.

При `useClones: false` материализация всё равно выполняется, но получает общие локальные данные. Их изменение или сохранение внутри возвращаемого экземпляра может сделать мутации видимыми другим читателям. Ошибки материализации передаются вызывающему коду; библиотека не возвращает исходное нематериализованное значение при ошибке.

## Сериализация

`FlashCache<L1Value, L2Value>` позволяет хранить разные типы в L1 и L2. Передайте сериализатор в `set()` и десериализатор в `get()` либо обе функции в `memoize()`. Они задаются для каждого вызова, а не в конструкторе.

```typescript
import { Redis } from 'ioredis';
import {
  FlashCache,
  FlashMemo,
  IORedisStore,
  MapStore,
  type JsonValue,
} from '@bidster/flash-cache';

const redis = new Redis();
const cache = new FlashCache<Date, JsonValue>(
  new MapStore<Date>(),
  new IORedisStore(redis),
  { ttl: 60_000, staleRatio: 0.8, namespace: 'dates' },
);
const memo = new FlashMemo(cache);
const serialize = (date: Date): string => date.toISOString();
const deserialize = (value: JsonValue): Date => {
  if (typeof value !== 'string') throw new Error('Expected an ISO date string');
  return new Date(value);
};

await cache.set('updatedAt', new Date(), serialize);
const result = await cache.get('updatedAt', deserialize);
const date = await memo.memoize('createdAt', () => new Date(), {
  serialize,
  deserialize,
  customTtl: 30_000,
});
```

Десериализация восстанавливает представление, которое хранится в L1, а не преобразует результат только для текущего читателя. Она выполняется только для данных L2 и должна возвращать значение, совместимое с типом L1. При попадании в L1 возвращается сохранённое локальное значение без вызова десериализатора. Если запись L2 свежая или устаревшая, но ещё допустимая, `get()` переносит десериализованное значение в L1, сохраняя исходные временные метки записи.

TypeScript разрешает `get(key)` или необязательный десериализатор, только если весь тип L2 совместим с типом L1. Например, `FlashCache<Date, string>` требует десериализатор при каждом чтении, а `FlashCache<string, string>` и общий `FlashCache<unknown, JsonValue>` допускают чтение без него. Без десериализатора данные L2 переносятся и возвращаются в сохранённом виде. Такое же требование совместимости действует для `memoize()` без настроек сериализации.

Все операции с одним ключом должны использовать согласованные типы значений и преобразования. Общий кеш может хранить разные типы под разными строковыми ключами, но TypeScript не проверяет эту договорённость для отдельных ключей. Прямое чтение из L1 с типом `unknown` сохраняет тип результата `unknown`, даже если передан десериализатор: попадание в L1 обходит его вызов. Сериализатор и десериализатор должны быть синхронными. Чтения L2 объединяются, но каждый вызов отдельно десериализует результат и переносит его в L1.

`IORedisStore` кодирует в JSON всю запись. Он принимает `JsonValue` и не восстанавливает автоматически такие типы, как `Date`, `Map` или экземпляры классов. Если значение L1 несовместимо с JSON, задайте явное преобразование.

## Запись, удаление и ошибки

- `await cache.set(key, value, serialize?)` сначала сериализует значение, синхронно записывает L1, затем ждёт запись L2. Ошибка записи L2 подавляется; новое значение L1 остаётся доступным.
- `await cache.del(key)` синхронно удаляет запись из L1, затем ждёт удаление из L2. Ошибка удаления L2 подавляется; оставшаяся запись L2 может снова заполнить L1 при следующем чтении.
- Ошибка чтения L2 обрабатывается как отсутствие записи в L2. Неистёкшее значение L1 всё ещё можно вернуть; иначе результат будет `miss` или `expired`.
- Ошибки L1, сериализатора и десериализатора передаются вызывающему коду. Ошибка сериализатора возникает до изменения хранилищ; ошибка записи или удаления L1 предотвращает соответствующую операцию L2.
- Ошибка загрузчика передаётся вызовам, ожидающим значение при промахе или истечении. Ошибки фонового обновления подавляются, если допустимое значение кэша уже возвращено. Неудачная загрузка не записывает замену и не продлевает прежний TTL; следующие вызовы могут повторить попытку.
- Ошибки клонирования и материализации передаются вызывающему коду, в том числе синхронно при синхронном попадании. Оба этапа выполняются после записи результата загрузчика, поэтому их ошибка не отменяет сохранение данных в кэше. Ошибка клонирования предотвращает материализацию; ошибка материализации затрагивает результат этого читателя, а не других вызовов, ожидающих общую загрузку.

Библиотека не логирует подавленные ошибки. При необходимости добавьте логирование или метрики в загрузчик либо адаптер хранилища. Автоматического расписания повторных попыток и настройки политики ошибок L2 нет.

### Одновременные операции

Запись и удаление не атомарны между хранилищами; операции одного ключа не выполняются строго последовательно. Ранее начатое чтение L2 может завершиться после `set()` или `del()` и перезаписать либо заново заполнить L1 старой свежей **или устаревшей** записью. Запись и удаление не отменяют выполняющиеся чтения и обновления; следующие читатели могут присоединиться к тому же запросу L2.

Объединение чтений L2 действует внутри одного экземпляра `FlashCache`, объединение загрузок — внутри одного экземпляра `FlashMemo`. Между экземплярами и процессами нет общей блокировки, потока инвалидации или координации обновлений. Если нужен строгий порядок, приложение должно самостоятельно координировать чтение, запись, удаление и фоновую работу.

## Хранилища и пространства имён

`MapStore<T>` расширяет `Map<string, StoreValue<T>>`. У него нет ограничения размера, политики вытеснения или автоматической очистки истёкших записей. Его можно использовать как L1, L2 в памяти или хранилище для тестов.

`IORedisStore` получает клиент `ioredis`, принадлежащий приложению. Он сохраняет JSON и использует Redis `SET ... PXAT expAt` для физического удаления по истечении срока. Подключение и поведение повторных попыток клиента настраивает приложение; оно же закрывает клиент при завершении. Для корректного абсолютного срока истечения часы приложения и Redis должны быть согласованы.

Пользовательский L1 реализует `Store<T>` с синхронными `get`, `set` и `delete`. L2 реализует `MayBeAsyncStore<T>` с теми же методами, возвращающими результат напрямую или через промис. Хранилища получают полные записи:

```typescript
interface StoreValue<T> {
  value: T;
  time: number;
  staleAt: number;
  expAt: number;
}
```

Совместимый синхронный LRU можно использовать как L1 напрямую. Храните записи `StoreValue<T>`, задайте нужную вместимость и учитывайте собственную политику вытеснения и TTL хранилища. `FlashCache` не задаёт ограничения размера и не запускает планировщик очистки.

Оба уровня используют один и тот же ключ с префиксом:

| Параметр | Ключ для `42` в хранилище |
| --- | --- |
| `namespace` не задан | `flashCache:v1:42` |
| `namespace: 'users'` | `flashCache:v1:users:42` |
| `namespace: false` | `42` |

### Случайное сокращение TTL

`jitter(ttl, percent = 0.1)` сокращает TTL на случайное целое число меньше `ttl × percent`. Используйте его при выборе TTL кэша или `customTtl` загрузчика, чтобы распределить моменты истечения:

```typescript
import { jitter } from '@bidster/flash-cache';

await memo.memoize('42', () => ({ name: 'Igor' }), {
  customTtl: jitter(60_000),
});
```

Утилита не проверяет аргументы; полученный TTL должен соответствовать требованиям кэша или мемоизации.

## Разработка и тесты

Из корня репозитория:

```bash
yarn install --frozen-lockfile
yarn build
yarn test
yarn test:types
```

`build` создаёт сборки ESM и CommonJS. `test` запускает модульные тесты и проверки поведения без интеграционных тестов Redis. `test:types` пересобирает пакет и проверяет контракты TypeScript.

Интеграционные тесты Redis используют Testcontainers и требуют Docker:

```bash
yarn test:integration
```

Этот скрипт задаёт `DOCKER_HOST` как сокет Docker Desktop `$HOME/.docker/run/docker.sock`. При другой конфигурации Docker запускайте Vitest напрямую со своим окружением:

```bash
yarn vitest run src/stores/ioredis-store.integration.spec.ts
```

## Бенчмарки

Команды бенчмарков находятся в отдельном пакете [`bench`](bench). В зафиксированном окружении используются Node.js 22.22.0 и npm 10.9.4. Перед запуском соберите корневой пакет:

```bash
yarn build
cd bench
npm ci --ignore-scripts
npm run bench

# Отдельные наборы
npm run bench:cache
npm run bench:memoize
npm run bench:overhead
npm run bench:flash-memo-cacheable
npm run bench:flash-cache

# Обратный порядок участников в сравнительных наборах
BENCH_REVERSE=1 npm run bench
```

Наборы покрывают чтение и промахи при загрузке по требованию, мемоизацию и SWR, накладные расходы поверх того же LRU, а также сравнение `FlashMemo.memoize` с `Cacheable.wrap`. В исходниках описаны нагрузка и проверки каждого набора. [Сохранённые результаты мемоизации](bench/flash-memo-cacheable.results.json) содержат сведения о запусках и хеши исходников; они относятся к измеренному состоянию кода, которое может отличаться от текущего.

Для локальной проверки регрессий `bench:baseline` записывает `bench/flash-cache.baseline.json`, а `bench:check` сравнивает с ним пропускную способность. Эти команды выполняются из пакета `bench`:

```bash
npm run bench:baseline
npm run bench:check
FLASH_CACHE_BENCH_THRESHOLD=0.1 npm run bench:check
```

По умолчанию допустимое падение пропускной способности — 15%. Сравнивайте результаты на одной машине и версии Node; при изменении нагрузки или реализации обновляйте baseline осознанно. Сохранённый baseline игнорируется Git.

Эти микробенчмарки в памяти не моделируют задержки Redis и сети, конкурентную нагрузку приложения или вытеснение записей. В некоторых наборах явно отключены клонирование и сериализация. Проверьте эти настройки перед сравнением с поведением `FlashMemo` по умолчанию и измеряйте нагрузку, с которой собираетесь работать.
