# Бенчмарки

Основные бенчмарки используют текущую сборку основного `FlashCache` через `../dist/cjs/index.js`. Сначала выполните `yarn build` в корне.

Без дополнительных зависимостей:

```sh
node --expose-gc bench/flash-cache.bench.mjs
BENCH_OUTPUT=/tmp/flash-cache-results.json node --expose-gc bench/flash-cache.bench.mjs
```

Покрываются fresh/stale L1, клонирование, L2, синхронные/асинхронные промахи и singleflight. Подготовка хранилищ исключена из времени. Для fresh L1 отдельно измеряется вызывающий код с `await`. Асинхронный store работает в памяти, без сетевых задержек. Stale измеряет выдачу значения при уже запущенном обновлении. Singleflight показывает время на читателя в группе из 32 вызовов.

Для сравнений с другими библиотеками установите зависимости в `bench` через `npm install`, затем:

```sh
npm run bench
npm run bench:get-or-set-cacheable
npm run bench:cpu
```

`bench` запускает cache-aside, getOrSet/wrap и сравнение накладных расходов с прямым LRU. CPU-бенчмарк запускает отдельные процессы и сохраняет результаты и профили. Для сравнений можно использовать `BENCH_REVERSE=1`.

## Исторические результаты

`v1-v2.results.json` содержит сравнение до удаления v1, включая повторный запуск с обратным порядком. `cpu-memo-wrap.results.json` и `flash-memo-cacheable.results.json` также относятся к прежней реализации. Их значения и названия участников не переписаны под новый API. Исполняемый код v1 не сохраняется: старые результаты служат только историческим ориентиром, новые замеры следует получать текущими скриптами.

## Сравнение до и после упрощения load

`load-refactor.bench.mjs` принимает путь к сохранённому `src/flash-cache.ts` до рефакторинга и сравнивает его с текущим исходником. Обе версии транспилируются одинаково через TypeScript; сборка `dist` не используется. Снимок старого исходника хранится отдельно от репозитория.

Для сравнения запускайте версии в отдельных процессах, чтобы избежать влияния общего JIT на порядок измерений:

```sh
BENCH_VERSION=before BENCH_OUTPUT=/tmp/load-before.json node --expose-gc bench/load-refactor.bench.mjs /tmp/flash-cache-before-load-refactor.ts
BENCH_VERSION=after BENCH_OUTPUT=/tmp/load-after.json node --expose-gc bench/load-refactor.bench.mjs /tmp/flash-cache-before-load-refactor.ts
```

Повторите пары несколько раз, меняя порядок. Без `BENCH_VERSION` версии чередуются в одном процессе; такой режим полезен для диагностики, но в этом сравнении заметно зависел от порядка и JIT. Каждый сценарий имеет 8 прогревочных и 21 измеряемый раунд. Подготовка исключена; GC перед замером принудительный, GC внутри замера учитывается. Store работает в памяти без сети. Stale full-cycle включает завершение обновления и запись в оба уровня, pending-refresh — только выдачу stale при уже запущенном обновлении. Singleflight измеряется на читателя в группе из 32 вызовов.

`load-refactor.results.json` содержит три независимых процесса на версию, медиану их медиан, исходные выборки, хеши исходников и диагностические прогоны в общем процессе. Подсчёт Promise выполняется отдельно от замеров времени:

```sh
node bench/load-refactor-promises.cjs /tmp/flash-cache-before-load-refactor.ts
```

Абсолютные счётчики включают Promise самого измерительного кода; сравнивается разница при одинаковой обвязке. Эти результаты относятся к указанным в JSON хешам, а не автоматически к последующим изменениям исходников.

### Удаление лишней Promise-цепочки

`load-optimization.results.json` содержит повторное сравнение трёх версий: `original` — до упрощения `load`, `simplified` — после упрощения, но до оптимизации Promise, `optimized` — после удаления лишней цепочки. Для каждой версии выполнены три независимых процесса тем же бенчмарком. В JSON сохранены хеши исходников, все выборки, порядок запусков и отдельные измерения числа Promise.

Для воспроизведения сравнения с промежуточной версией используйте те же команды, передав её снимок `/tmp/flash-cache-before-promise-optimization.ts`. Снимки в `/tmp` временные; для более позднего воспроизведения их нужно сохранить отдельно.
